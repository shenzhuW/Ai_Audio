# 真实浏览器截图与操作说明

这 14 张图来自本轮同一套生产构建和真实 PostgreSQL 测试库，不是原型图。浏览器为 Chromium，桌面 1440×1080，窄屏 390×844。完整页面截图会比视口更长。[verification.json](verification.json) 记录 URL、时间、截图 SHA256、项目/修订/jobId 与真实响应结果。

## 操作流程与截图

| 步骤 | 操作及预期 | 实际截图 |
|---|---|---|
| 1 | 创建专用项目→研究页输入正文→创建草稿→刷新。正文恢复、可编辑，手动内容标“未核实” | [01 草稿](01-draft.png) |
| 2 | 两个标签页打开同一草稿。B 保存新内容；A 保留旧编辑版本再保存，返回 409。A 本地文本保留，有重载按钮；点击后读取 B 的版本 | [02 冲突提示](02-conflict-409.png) |
| 3 | 当前草稿提交审核。正文变只读，出现审核意见、批准/驳回操作 | [03 待审核](03-submitted.png) |
| 4 | 批准当前修订→刷新。显示已批准、下游 jobId，原地保存入口消失。额外发 PATCH 返回 422；新库直接 SQL UPDATE 也被拒绝 | [04 批准只读](04-approved-readonly.png) |
| 5 | 点击“创建新修订”。生成 v2 草稿，UUID 不同、parentRevisionId 指向 v1；修改不会写入 v1 | [05 新修订](05-fork-new-revision.png) |
| 6 | 修改 v2→保存→提交→填写驳回意见→驳回→刷新。意见、状态保留；需继续 fork 才能编辑 | [06 驳回](06-rejected.png) |
| 7 | 历史列表选择 v1。原批准正文和历史仍可读取，正文只读 | [07 历史批准版](07-approved-history.png) |
| 8 | 创建并批准引用研究 v1 的文稿；再 fork/批准研究新版。文稿仍固定旧 revisionId，出现依赖失效；历史 approved 不被改写 | [08 依赖失效](08-dependency-stale.png) |
| 9 | 返回总览、刷新。阶段、依赖失效计数及任务均来自真实快照 | [09 总览](09-overview-dependencies.png) |
| 10 | 新建独立项目，点击“生成模拟研究文本”。只创建真实 queued jobId，没有提前展示生成结果 | [10 Mock 排队](10-mock-job-queued.png) |
| 11 | 在相同测试配置下运行 Worker 一轮。任务成功，新修订为 draft、mock=true，界面显示“Mock · 未核实” | [11 Mock 草稿](11-mock-draft.png) |
| 12 | 编辑 Mock 草稿并创建新修订。v1/v2 均保留 Mock 标签，没有变成“已核实” | [12 Mock 标签继承](12-mock-edited-fork.png) |
| 13 | 独立项目批准无上游的文稿→运行 Worker。配音提供方未接通，显示失败说明，resultRevisionId=null，无假音频 | [13 提供方失败](13-provider-unconfigured.png) |
| 14 | 改为 390px 宽度打开研究页。栏位折叠，保存/提交等按钮和 Mock 标签仍可用，无横向溢出 | [14 窄屏](14-mobile-390.png) |

步骤 8 的文稿初始建立/批准及步骤 13 的独立文稿使用真实 API 准备，界面截图读取真实数据库状态。其余审核主要流程通过真实 UI 操作。并发批准/幂等重放通过真实并行 HTTP 请求核验，浏览器冲突图专门展示双标签页保存冲突；不把两种场景混为一谈。

## 数据与操作注意

测试项目名称明确含“Phase 01 最终验收”。如需人工复查项目，可从 verification.json 取得 database 与截图 URL，再用该独立测试库和同一运行的 `.cache/phase01-final/<run>/postgresql` 原件目录启动；不要将真实用户应用切到测试库。截图地址在应用停止后不会自动保持可访问，PNG 与 JSON 证据可离线审阅。

本轮的保护行为、HTTP 响应和审核状态均是真实功能；Mock 仅指生成文本。批准 Mock 不会洗掉来源标识，也不表示事实验证或素材许可已经完成。
